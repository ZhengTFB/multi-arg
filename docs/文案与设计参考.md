# 文案与设计参考

给 Claude Code 用的写作文档。写界面文字之前先读这一页。

---

## 一、调性：克制专业

参考 Apple 中文官网、Linear、Stripe、Sumeria。共同点：字少，词准，不解释自己有多好。

反面参考：写着"开启你的探索之旅""一站式解决方案""让每一次探索都值得"的东西。

**克制不等于冷淡。** 该有的礼貌要有（"请稍候"不是废话），该给的出路要给（错误提示必须说下一步）。

---

## 二、要清的三种东西

它们经常被混为一谈，处理方式不同。

### 1. AI 味 —— 删

模型的指纹，和内容无关。

- 否定式排比："不是 A，而是 B""不只是 X，更是 Y"
- 硬凑三项："创新、灵感、洞察"里通常有一项是凑的
- 结尾升华：把一件具体的事接到"这意味着……"上
- 句尾挂 -ing 式分析："……，彰显了团队的实力"
- 模糊归因："业内认为""有专家指出"，给不出来源的
- 通用积极结尾："未来可期""迈出了重要一步"
- "值得注意的是""不难发现"

### 2. 黑话 —— 枪毙

赋能、闭环、抓手、颗粒度、打通、链路、对齐、沉淀、心智、势能、组合拳。

这些不是 AI 的发明，是行业的病。但 AI 学得很快，所以看起来像。

### 3. 土 —— 改

审美问题。"开启探索之旅""让每一次\_\_\_\_都值得"这种句式，AI 爱写，但人不写是因为俗。

改法不是换成大白话，是**换成具体的事**。

| 土 | 改 |
| --- | --- |
| 开启你的探索之旅 | 粘贴游戏链接，开一个房间 |
| 让线索不再散落 | 谁看到什么，都会出现在这里 |

## 三、判断标准只有一句

> **删掉它，信息或语气有损失吗？**

有损失就留，没损失就是填充。

按这条看：

- "加载中，请稍候" —— 删掉"请稍候"，丢的是礼貌和节奏。**留。**
- "这个网页不支持嵌入" —— 别改成"这个网页不让嵌"。后者听着随便，还把技术原因说糊了。**留原文。**
- "高效的多人协作体验" —— "高效"是填充，"多人协作"是信息。可以留，但能更好。

## 四、按位置分层

不同位置的文字，标准不同。

### 界面控件

用行业通行说法，不创新。

`开始` `取消` `保存` `删除` `发出去` `重试` `返回`

状态用标准语：`加载中` `已保存` `连接断开` `正在重连`

不要写"确认执行该操作"，写"确定"。

### 宣传位

首页标题、副标题、空状态的引导语。可以有力，但每个形容词要对得上一个事实。

```
✗ 高效的多人协作体验
✓ 各查各的，看到什么丢进来

✗ 让解谜更简单
✓ 谁翻到了新的一页，你们都能点进去
```

第二行不煽情，但它能被验证。这比第一行强的地方不在于"大白话"，在于**它说了具体的事**。

### 错误提示

三段式：出了什么事 → 为什么 → 怎么办。

```
✗ 操作失败
✓ 这个网页不支持嵌入。点"在新窗口打开"试试。
```

```
✗ 网络异常，请稍后重试
✓ 连接断了，正在重连。数据都在，不用刷新。
```

第二句多出来的那半句（"数据都在"）是关键。用户此刻怕的是丢东西。

### 空状态

可以有一句人味的话，但不用感叹号，不卖萌。

```
流的空状态：  还没有人发东西。
笔记的空状态：想到什么写什么。
关键词的空：  还没有记录。试试 `符咒 = 命中`。
人物关系的空：加第一个人。
```

## 五、这个产品的具体文字

**这一节是举例，不是清单。** 项目和按钮实际的文字以 `05-视觉与文案.md` 第 5 节那张表为准，两边冲突时以那张表为准，然后回来把这里改掉。

**首页**

- 标题：`几个人一起玩网页解谜`
- 输入框占位符：`粘贴游戏链接`
- 推荐区标题：`推荐`
- 底部小字：`有房间号？`

**配置页**

- 区块标题：`游戏` `你的名字` `这局要开哪些`
- 模块说明：`开了全员可见，进房后不能改。`
- 主按钮：`开始`

**房间**

- 发送按钮：`发出去`
- 输入框占位符：`说点什么…`
- 快捷语法提示：`词 xxx = 命中 · 密 账号 / 密码 / 用途`
- 拿不到地址：`这页拿不到地址。长按游戏里的链接拷一下，再回来。`
- 代理失败：`这一页可能没加载完整。` + `换直连`
- 快到期：`这个房间还有 1 天到期。要留个底吗？`
- 导出按钮：`导出`

**错误**

- 网站不让嵌：`这个网页不支持嵌入。`
- 房间不存在：`没有这个房间。看看房间号对不对。`
- 断线：`连接断了，正在重连。`
- 房间已过期：`这个房间已于 11 月 6 日到期。`

## 六、给 Claude Code 的约束（可直接粘）

```
写界面文字前遵守：

调性：克制专业。参照 Apple 中文官网、Linear、Stripe。

禁止：
- 否定式排比（"不是 X，而是 Y"）
- 为凑数硬排三项
- 结尾升华、通用积极结论（"未来可期"）
- 模糊归因（"业内认为""专家指出"）
- 黑话：赋能、闭环、抓手、颗粒度、打通、链路、沉淀
- 感叹号
- "开启……之旅""让每一次……都值得"这类句式

要求：
- 界面控件用行业通行说法，不创新。
- 错误提示必须包含"怎么办"，并说明数据是否安全。
- 空状态写具体场景，不写"暂无数据"。
- 每个形容词要能对上一个事实，对不上就删。

自检：把每句话的形容词去掉，还剩信息吗？不剩就是空话。
```

## 八、视觉基准

**以 **`设计参考/`** 里的 HTML 为准，这一节只是背景。**

那套设计来自 Sumeria（法国 Lydia 的银行 App），用户觉得合适，就拿来当骨架：

- 骨架：一张主卡 + 一条流水，没有底部导航栏
- 主色：墨绿 `#07444C`，次色 `#1C5F6D`
- 底色：米白 `#F4F2ED`
- 大字、大留白、圆角卡片
- 材质感靠玻璃和极轻的投影，不靠渐变和描边

这里是概括，不是数值来源。**数值看 **`设计参考/`**，冲突时以它为准。**
