## 1. 数据模型

```ts
type Room = {
  id: string                 // 4 位数字
  tokenHash: string          // SHA-256(token)，不存明文
  createdAt: number
  expiresAt: number          // createdAt + 7 天
  game: {
    url: string
    origin: string
    title: string
    proxy: boolean           // 默认 true
    embeddable: boolean      // probe 结果
    hasSearch: boolean
    searchParam?: string     // 从 games.json 带过来，默认 'q'
  }
  modules: Module[]          // ['note','keyword',...]
}

type Member = {
  id: string
  name: string
  color: string              // 见 2.2
  joinedAt: number
  lastSeen: number
  current?: { url: string, title: string, at: number }
}

type Item = {
  id: string
  type: 'link' | 'note' | 'keyword' | 'person' | 'secret' | 'event' | 'system'
  authorId: string
  createdAt: number
  starred?: boolean
  status?: 'open' | 'confirmed' | 'excluded'
  pageUrl?: string           // 记这条时在哪个页面
  refId?: string             // 接在别人那条下面的评论
  mentions?: string[]        // memberId
  url?: string
  title?: string
  text?: string
  keyword?: string
  result?: 'hit' | 'miss'
  person?: { name: string, note?: string }
  relations?: { from: string, to: string, label: string }[]
  secret?: { account: string, password: string, usage?: string, verified: boolean }
  event?: { at: string, text: string }
}
```

**关键约束**：一条 item 只有作者能改。别人只能新建一条带 `refId` 的 note 接在后面。

所以不存在并发写冲突，不需要 CRDT，不需要 OT。两个人同时想改同一条，第二个人在界面上根本没有"编辑"入口。

## 2. 存储

### 2.1 用 SQLite，不要塞一个大 JSON

DO 单个 value 上限 128KB。1000 条笔记塞进一个数组会超，而且每加一条都要全量读写。

```sql
CREATE TABLE IF NOT EXISTS items (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,
  author_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  starred INTEGER DEFAULT 0,
  status TEXT DEFAULT 'open',
  page_url TEXT,
  ref_id TEXT,
  body TEXT NOT NULL,          -- 其余字段序列化
  mentions TEXT
);
CREATE INDEX IF NOT EXISTS idx_items_created ON items(created_at DESC);

CREATE TABLE IF NOT EXISTS members (
  id TEXT PRIMARY KEY, name TEXT, color TEXT,
  joined_at INTEGER, last_seen INTEGER
);

CREATE TABLE IF NOT EXISTS meta (
  k TEXT PRIMARY KEY, v TEXT
);
```

- 进房只加载最近 500 条：`ORDER BY created_at DESC LIMIT 500`。往上滚到顶再加载 500 条。
- 写入：`INSERT` 一条然后广播。不要"读全量 → 改 → 写回"。
- 房间元信息放 `meta`，key 用 `room`。

### 2.2 成员配色

固定 10 色，按加入顺序取，不做随机（随机会撞色）：

```ts
['#07444C', '#8C4A2F', '#3F5B8C', '#6B4A78', '#2F6B4A',
 '#8C6B2F', '#4A4A4A', '#7A2F3F', '#2F6B72', '#5A5A2F']
```

用完第 10 个从第 1 个重来，改用浅一档的变体。

## 3. 创建与加入

### 3.1 创建

`POST /api/room`

```json
{ "url": "...", "name": "...", "modules": ["note","keyword"] }
```

服务端：

1. 生成 4 位 id（`1000`–`9999`）。`idFromName` 取 DO，如果已有状态就重生成，最多 20 次。
2. 生成 token：`crypto.getRandomValues(new Uint8Array(32))` 转 hex，只返回一次，库里存 SHA-256。
3. 初始化 DO，写 meta，建表。
4. 返回 `{ id, token, frameUrl }`。`frameUrl` 是签过名的代理地址（见 03 §1）。

**撞号自动换，不报错。** 前端不需要知道。

### 3.2 加入

`wss://host/ws/<id>?token=<token>`

DO 收到后：

1. 有 token 就校验（常量时间比较）。不匹配 → `401` 并关闭。
2. 校验 `expiresAt`。过了 37 天 → `410`。
3. 找 member：同 token 已存在就复用，否则新建。
4. 发快照 `{ t:'hello', room, items, you:{ id } }`。
5. 广播 `{ t:'join', member }`。

**没有 token 也能进**：不带 token 时视为"报房间号进来"，允许加入。这条路要限流（见 6）。

### 3.3 重新拿代理地址

刷新页面时 iframe 的 src 从 `sessionStorage` 取。没有就调：

```
GET /api/frame?r=<id>&token=<token>
```

返回一个新的签名地址。不要每次刷新都重建房间。

## 4. 消息

### 4.1 协议

客户端 → 服务端：

| t | 载荷 | 说明 |
| --- | --- | --- |
| `item.add` | `{ item }` | 服务端补 id、authorId、createdAt 后广播 |
| `item.patch` | `{ id, patch }` | 只有作者能改，服务端校验 authorId |
| `page` | `{ url, title }` | 当前页变化，节流 5 秒 |
| `typing` | `{ on }` | v1 不做 |

服务端 → 客户端：

| t | 载荷 |
| --- | --- |
| `hello` | `{ room, items, you }` |
| `join` / `leave` | `{ member }` |
| `item.add` / `item.patch` | `{ item }` |
| `presence` | `{ members }`，节流 3 秒 |

**服务端要防的**：客户端传来的 `authorId`、`createdAt`、`id` 一律忽略，用服务端生成的。不校验的话，谁都能伪造别人发消息。

### 4.2 断线

指数退避 1s / 2s / 4s / 8s，上限 15s。重连成功**拉全量最近 500 条**，不做增量补发。房间里数据量小，全量最简单。

## 5. Hibernation

必须用 `state.acceptWebSocket(server)`，不要用 `server.accept()`。

理由：`accept()` 会让 DO 全程保持唤醒，一个开着的房间按小时计费。Hibernation 期间 DO 睡过去，有消息才醒。成本差一个数量级。

对应要写三个 handler，不要塞进 `fetch`：

```ts
async webSocketMessage(ws, msg) {}
async webSocketClose(ws, code, reason) {}
async webSocketError(ws, err) {}
```

## 6. 房间号枚举与限流

4 位数字一共 9000 种。不防护的话，脚本几分钟扫完全部房间。

三条：

1. **按 IP 限流**：同一 IP 每分钟最多 6 次"用房间号加入"，超了返回 `429`，提示 `试得太快了，等一分钟。`
2. **失败计数**：同一 IP 连续 20 次失败，封 1 小时。计数放 DO 的 `meta`，key 用 IP 的哈希，不要存明文 IP。
3. **房间不存在和 token 错误返回同一句话**，不区分。不给扫描器判断依据。

这做不到绝对安全，但把成本抬到了"不值得"。

## 7. 房间隔离

- 每个房间一个 DO 实例，`idFromName(roomId)`。数据物理隔离，代码里没有跨房间查询的路径。
- 任何 API 先解析 `roomId`，再取 DO。不要在 Worker 层维护全局表。
- token 只返回一次，服务端只存哈希。
- 全站 HTTPS / WSS，Cloudflare 默认。不要自己写加密。

**这套隔离是"房间之间"，不是"房间之内"。** 知道 4 位房间号就能进（产品要求，见 3.2），所以同房间内没有身份验证——谁进来都是成员。别在界面上暗示"只有拿到链接的人能看"，也别写"端到端加密"这种话。防的是跨房间串数据，不是防同房间的人。

## 8. 过期

DO 里设 alarm 到 `expiresAt`：

- **第 7 天**：`meta.expired = true`，房间只读，内容保留 30 天。
- **第 37 天**：删表，删 meta。
- **第 6 天起**，流顶部一条不打扰的提示：`这个房间还有 1 天到期。要留个底吗？` 后面一个"导出"文字按钮。
- 提示每天只出现一次（`localStorage` 记日期），关掉当天不再出现。

只读状态下的表现见 01 §3。
